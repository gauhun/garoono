<h2>What the research found</h2>
<p>On September 25, 2026, UpGuard published a study of roughly 300,000 domains that use Supabase (<a href="https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps" target="_blank" rel="noopener noreferrer">UpGuard</a>)<br>It found 16,326 databases exposing readable tables to anyone (<a href="https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps" target="_blank" rel="noopener noreferrer">UpGuard</a>)<br>Over half of those databases had indicators of personal data (<a href="https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps" target="_blank" rel="noopener noreferrer">UpGuard</a>)</p>
<p>Indie makers are not immune<br>A January 2026 scan of 20,052 products listed on indie launch directories found 11.04% of domains exposing Supabase credentials (<a href="https://supaexplorer.com/cybersecurity-insight-report-january-2026" target="_blank" rel="noopener noreferrer">SupaExplorer report</a>)<br>TrustMRR listings had the highest rate at 23.76% (<a href="https://supaexplorer.com/cybersecurity-insight-report-january-2026" target="_blank" rel="noopener noreferrer">SupaExplorer report</a>)</p>
<blockquote>
<p>The pattern is almost always the same: a table without Row Level Security, reached with a key that was meant to be public</p>
</blockquote>
<h2>Why vibe coded apps leak</h2>
<p>Supabase turns on Row Level Security by default for tables you create in its Table Editor<br>UpGuard points out the gap: tables created programmatically through the API, which is how coding agents talk to Supabase, do not get RLS by default (<a href="https://www.upguard.com/blog/everything-everywhere-systemic-data-exposure-in-supabase-apps" target="_blank" rel="noopener noreferrer">UpGuard</a>)</p>
<p>So the agent creates <code>profiles</code>, <code>orders</code> and <code>messages</code>, the app works, and every row is readable<br>Nothing looks broken, which is exactly why nobody notices</p>

<h2>Is the Supabase anon key safe in my app?</h2>
<p>Yes, if RLS is on<br>Supabase says the publishable key is safe to expose in a web page, a mobile app or source code, and that it only reaches what Row Level Security allows (<a href="https://supabase.com/docs/guides/api/api-keys" target="_blank" rel="noopener noreferrer">Supabase docs</a>)</p>
<p>The secret key is a different animal<br>Supabase says a secret key bypasses every Row Level Security policy you have, and to never put one in a browser, a shipped application or source control (<a href="https://supabase.com/docs/guides/api/api-keys" target="_blank" rel="noopener noreferrer">Supabase docs</a>)<br>If your AI agent pasted a secret or <code>service_role</code> key into client code, treat it as leaked and rotate it</p>
<h2>The October 30, 2026 change you should know about</h2>
<p>Until now, new tables in the <code>public</code> schema were automatically exposed to the <code>anon</code>, <code>authenticated</code> and <code>service_role</code> roles (<a href="https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically" target="_blank" rel="noopener noreferrer">Supabase changelog</a>)<br>From October 30, 2026, existing projects stop getting those automatic grants, and new tables need explicit grants to be reachable through the API (<a href="https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically" target="_blank" rel="noopener noreferrer">Supabase changelog</a>)</p>
<p>This is good for security, but it can break an app that silently relied on the old behaviour<br>Add grants on purpose, table by table, and only the ones each role needs</p>
<h2>The 9 step checklist</h2>
<h3>1 Find every table without RLS</h3>
<p>Run this in the Supabase SQL editor</p>
<pre><code class="language-sql">select tablename, rowsecurity
from pg_tables
where schemaname = &#39;public&#39;
order by rowsecurity, tablename;
</code></pre>
<p>Any row with <code>rowsecurity = false</code> is open to whatever the grants allow</p>
<h3>2 Turn RLS on for all of them</h3>
<pre><code class="language-sql">alter table public.profiles enable row level security;
</code></pre>
<p>With RLS on and no policies, the API returns nothing, which is the safe starting point</p>
<h3>3 Write the narrowest policy that works</h3>
<p>The most common one: a signed in user can read only their own rows</p>
<pre><code class="language-sql">create policy &quot;Users read own rows&quot;
on public.profiles for select
to authenticated
using ((select auth.uid()) = user_id);
</code></pre>
<h3>4 Add separate policies for insert, update and delete</h3>
<p>Use <code>with check</code> so a user cannot write rows that belong to someone else<br>Skip any operation your app does not need</p>
<h3>5 Grant access on purpose</h3>
<p>Give <code>anon</code> only what logged out users truly need, often nothing<br>Give <code>authenticated</code> only the operations your policies cover</p>
<h3>6 Test like an attacker</h3>
<p>Call the REST endpoint for each table with only the publishable key and no user session</p>
<pre><code class="language-bash">curl &quot;https://YOUR_PROJECT.supabase.co/rest/v1/profiles?select=*&quot; \
  -H &quot;apikey: YOUR_PUBLISHABLE_KEY&quot;
</code></pre>
<p>You want an empty list or an error, never real rows</p>
<h3>7 Keep secret keys on the server</h3>
<p>Secret keys belong in Edge Functions or your own server, never in a Flutter build, a React bundle or a public repo<br>Anything shipped inside an app can be extracted</p>
<h3>8 Move AI provider keys behind a function</h3>
<p>The same rule applies to OpenAI or Gemini keys in AI wrapper apps<br>Even Firebase, whose normal API keys are fine to ship, says a Gemini Developer API key should never be included in your code or configuration files (<a href="https://firebase.google.com/docs/projects/api-keys" target="_blank" rel="noopener noreferrer">Firebase docs</a>)</p>
<h3>9 Tell your agent the rules up front</h3>
<p>Paste this into your project rules file so every new table starts locked</p>
<blockquote>
<p>Every table you create in Supabase must have Row Level Security enabled in the same migration<br>Add an explicit policy for each operation the app uses, and explicit grants per role<br>Never use or print the service role key in client code</p>
</blockquote>

<h2>Using Firebase instead?</h2>
<p>The idea is the same with different names<br>Firebase says its API keys do not need to be treated as secrets, and that data security is enforced by Firebase Security Rules, not by hiding the key (<a href="https://firebase.google.com/docs/projects/api-keys" target="_blank" rel="noopener noreferrer">Firebase docs</a>)<br>So the Firebase version of this checklist is: no test mode rules in production, rules that check <code>request.auth</code> on every collection, and App Check for extra protection</p>
